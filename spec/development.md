# Development context

- Implementation: Rust/Axum HTTP kernel, SQLite storage, delegated OIDC and separate MCP OAuth, service adapters, React portal and Docker Compose. Services default to disabled until an administrator records provider verification.
- [Setup and commands](../README.md); locked dependencies are in `Cargo.lock` and `package-lock.json`. All direct versions matched the latest stable official Cargo/npm registry releases on 2026-10-19.
- `src/` contains the kernel, identity, OAuth, HTTP/UI and storage. `src/modules/` owns service registration, input/result schemas, resources and provider adapters linked to their upstream references. Module-owned HTTP routes use `/modules/{module_id}/...` and shared access middleware. `web/` contains the portal and MCP card resource. `test/` contains Rust integration tests, browser tests and public OIDC signing fixtures.
- The native server requires `npm run build` first and reads exported environment variables; Compose interpolates required variables from `.env` or the platform. `compose.yaml` only exposes port 3000 for a proxy network (Coolify-compatible); `compose.override.yaml` adds the local `127.0.0.1:3000` binding. All externally generated URLs use `PUBLIC_URL`; forwarded headers are ignored. HTTPS terminates at an operator-managed proxy/tunnel.
- Browser sessions expire after eight hours; OAuth transactions after ten minutes, client codes after two minutes, MCP access tokens after fifteen minutes and rotating refresh tokens after thirty days. Service access uses [personal API tokens](identity.md#infomaniak-authorisation) checked against the signed-in profile and stored per user/service; they do not renew. Disconnect removes local credentials; employees delete the token in Infomaniak to invalidate it upstream.
- A single process owns SQLite with WAL and foreign keys. AES-256-GCM binds encrypted credentials/transactions to their user/service or flow; a database sentinel rejects an incorrect key. Bearer tokens and session identifiers are stored as hashes. Audit retention is thirty days, capped at 10,000 rows. There are no schema migrations; incompatible development schema changes require fresh development storage.
- Client registration supports public clients (`none`) and PKCE S256, HTTPS and loopback callback URLs. Client metadata URLs are not fetched. Each new client connection requires explicit browser consent. Grants combine the highest user/group level; local write grants include read capability, while client read/write scopes remain explicit.
- OAuth scope discovery and consent validation derive service IDs from the module registry. Access checks reread the exact bearer token/current grant or browser session after upstream renewal, so concurrent client revocation, refresh-family invalidation, logout or session expiry prevents dispatch.
- Validated identity changes at login/renewal update the existing `(iss, sub)` account before domain rejection, closing older browser and service access when the latest verified email becomes ineligible. Unverified claims and a different refresh-token subject never update that account.
- MCP authorisation failures, including upstream reconnection failures, retain HTTP 401/403 and missing-scope challenges across tool and resource dispatch, including failures after partial mail operations. Every module records known object selectors and the mutation phase before writing; these survive provider failures and tool deadline cancellation in text and `_meta`, or HTTP error context. Mail retains draft UUIDs and attachment upload progress. Recovery context excludes content/secrets and is never written to audit logs. Reject mismatched draft/event identities, invalid calendar identities and control characters in outgoing/provider mail headers before writes/uploads; invalid draft creation results report uncertainty. Multiline message bodies remain supported.
- Transfers are inline MCP images/resources, limited to 8 MiB; mail attachment inputs are `{filename, mime_type, base64_content}` objects. No tool reads local paths. kDrive resource discovery lists files previously observed by that user through tools and rechecks them upstream; templates/direct reads work without prior discovery.
- kDrive tool lists request 50 items and expose provider cursors; mail message/draft lists expose numeric `next_offset` alongside the string cursor. Resource discovery uses stable row boundaries so pruning stale or inaccessible references does not skip later files. Provider 404s are safe `provider_not_found` errors.
- kDrive validates provider file/drive identities before returning metadata, discovery caching or downloads. Uploads/folder creation require usable file identities; file-mutation acknowledgements may omit identities but validate any returned IDs. Invalid results retain known destinations and safe returned file/drive IDs as uncertain outcomes. Sharing response IDs are not interpreted as file IDs.
- Provider HTTP requests have five-second connection and twenty-second total timeouts, disabled redirects and explicit no-retry policy. Tool/resource calls have ninety/sixty-second deadlines. Non-idempotent server/transport/deadline failures report uncertainty. Calendar listing requires a positive interval of at most 366 days; oversized result sets require a narrower interval. Ambiguous/nonexistent local times require explicit offsets.
- Calendar validates event/result identities and any returned calendar identity, including optional IDs in deletion acknowledgements, retaining safe returned event IDs in uncertain mutation recovery context. Offset-free inputs use the profile timezone, retaining each existing event timezone when possible. Explicit instants in a repeated local hour use UTC in the provider payload to avoid losing their offset; omitted times remain untouched. Listing bounds in a repeated local hour currently fail with `provider_limitation`: the reference provider query uses wall times and cannot preserve the offset. Bounds outside that hour can enclose the transition; full offset-bound support remains required pending provider evidence. Notification metadata distinguishes requests accepted by the provider from notifications not requested; delivery still needs live confirmation.
- Mail validates reused recipients, sender/reply headers and attachment metadata before uploads, and provider mailbox/folder/upload identifiers before reuse. Read/reply sources require matching message UIDs and any returned folder/mailbox IDs; numeric/scoped UIDs remain intact. Listings derive actual folders from scoped UIDs or folder metadata and reject conflicting identities; global search never substitutes its Inbox query base. Draft reads/creation require UUIDs; mutation acknowledgements must be objects and validate any returned UUID against the requested draft. All draft results validate any returned mailbox identity; uncertain mutation errors retain safe returned UUIDs. Malformed folder-creation results report uncertainty with parent-folder context, also retained across tool deadlines. Sending-identity lookup validates hosting/mailbox path selectors; 401/403 responses stop the operation, while unavailable lookup metadata and other lookup failures retain explicit fallback warnings. Calendar cards use `https://ksuite.infomaniak.com/calendar`; provider event deep links remain unverified.
- [Shared specifications](README.md) define cross-module requirements; `spec/modules/` defines service capabilities; [AGENTS.md](../AGENTS.md) defines agent instructions.
- Before implementing identity, resolve the [provider prerequisites](identity.md#before-implementation).
- After documentation changes, verify local Markdown links and preserve existing requirements.

## Local ChatGPT testing

- Run the server locally; expose the whole application through a stable HTTPS tunnel. [sish](https://github.com/antoniomika/sish) supports SSH forwarding through a public gateway.
- Example: gateway `tunnel.example.org`, dev origin `https://mcp-dev.tunnel.example.org`, local server `127.0.0.1:3000`.
- Provision gateway DNS/TLS and authorised SSH keys; require the requested hostname instead of random assignment. See [sish configuration](https://docs.ssi.sh/advanced).

Example tunnel after gateway setup:

```sh
ssh -p 2222 -o ExitOnForwardFailure=yes \
  -R mcp-dev:80:127.0.0.1:3000 tunnel.example.org
```

- Set `PUBLIC_URL` to the dev HTTPS origin; forward `/mcp`, discovery, OAuth, callback and UI routes. Generate external URLs from `PUBLIC_URL`; trust forwarded headers only from configured proxies.
- Use separate development SQLite storage, encryption key and Infomaniak application credentials. Register `PUBLIC_URL` + `/auth/infomaniak/callback` with that application; ChatGPT's OAuth redirect remains a separate client registration.
- Preserve authentication headers and Streamable HTTP/SSE, including quiet intervals. Keep sish capture consoles disabled and redact OAuth queries/credentials from gateway logs.
- Keep normal authentication/domain checks; use manual approval and limited service grants for development testers.
- In [ChatGPT Plugins](https://chatgpt.com/plugins), choose **Add custom MCP server**, enter the dev HTTPS URL ending in `/mcp`, configure OAuth and connect. Workspace permissions apply. Follow [official connection steps](https://developers.openai.com/plugins/deploy/connect-chatgpt).
- Restart locally to test changes; refresh the ChatGPT connection after tool/schema/auth/UI changes, then retest. A hostname change also requires updated OAuth registrations and client reconnection.

[Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) is an alternative for supported OpenAI clients. It transports private MCP calls; the browser-facing OAuth server still needs a reachable endpoint.
